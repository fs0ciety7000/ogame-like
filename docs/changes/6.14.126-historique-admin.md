## Demande
Lot AA8 : différence champ par champ dans le journal des versions de contenu ; retour arrière d'un seul groupe de règles (au lieu de
toute la section « rules ») ; instantanés étendus aux réglages serveur hors `CONTENT_SECTIONS` (`casino`, `procedural`,
`announcements`, `banners`, `emojis`, `staff`). Le serveur fait autorité (route admin `isGameAdmin`, garde de contenu
`guardContentConfig` sur le retour arrière).

Vu par l'admin : le journal disait « avant modification · 12 Ko » sans dire quoi ; revenir en arrière sur les règles annulait tous les
groupes à la fois (un réglage du casino fait entre-temps aussi) ; casino, générateurs, annonces, bandeaux, émojis et équipe n'avaient
aucune trace.

## Diagnostic
- `cosmic_db.js` (`saveContentVersion`, `snapshotContent`, `contentRollback`) : instantané seulement pour `CONTENT_SECTIONS` ; le
  retour arrière réécrivait la section entière **sans validation** (une version d'avant un changement de règle pouvait réintroduire une
  valeur aujourd'hui refusée par `guardContentConfig`).
- `ContentHistoryPanel.tsx` : liste et bouton « Revenir », aucune comparaison.
- Réglages écrits par des routes (casino : `adminCasino` ; générateurs : `adminProcedural` ; équipe : `adminManage`) : pas de requête
  sur `game_config`, donc pas d'instantané ; le casino et les générateurs mêlent réglages et état de jeu (pot, tournois, journal).

## Ce qui change
- Pour le joueur : sans objet.
- Pour l'admin (Admin → Contenu → Journal de contenu) :
  - **« Ce qui a changé »** sur chaque version : la différence champ par champ entre cette version et l'état qui l'a suivie (version
    suivante de la même section, ou contenu actuel) : « changé combat.maxRounds 6 → 9 », « ajouté alliances.researches[soutes] … » ;
    listes comparées par identifiant, 200 lignes au plus ;
  - **« Revenir pour un seul groupe »** (section Règles) : un bouton par groupe de règles qui a changé ; seul ce groupe reprend l'état
    de la version, les autres restent tels quels ; confirmation ;
  - réglages du serveur dans le journal : Casino (réglages), Générateurs (réglages), Annonces, Bandeaux, Émojis, Équipe (rôles) ;
    filtres par réglage ; l'équipe affiche « Historique seul » (ses rôles suivent les administrateurs et les titres des joueurs) ;
  - un retour refusé par la garde de contenu affiche la raison (« Règles refusées : … »).
- Dans le code :
  - `contentHistory.ts` (nouveau, moteur) : `SETTINGS_HISTORY`, `isSettingsHistoryKey`, `settingsSnapshot`, `restoreSettings`,
    `diffValues`, `shortJson`, `changedRuleGroups`, `rollbackRuleGroup` ;
  - serveur (`cosmic_db.js`) : `assertContentValid` (garde commune à l'enregistrement et au retour), `snapshotContent` étendu aux
    réglages suivis (partie réglée, rien si elle n'a pas changé), `saveSettingsVersion` (casino, générateurs, équipe), `contentRollback`
    avec `group` et les réglages suivis ; exports (`hooksEntry.ts`) ;
  - admin : `ContentHistoryPanel.tsx` (différence, retour d'un groupe, libellés des réglages, dates par `formatDateTime`) ;
  - `designSystem.test.ts` : `ContentHistoryPanel.tsx` retiré du cliquet des dates (repris).

## Migration
Sans objet : `content_versions` garde son schéma (section texte de 60 caractères) ; les versions d'avant restent lisibles et
restaurables. Aucune donnée de joueur touchée.

## Décisions et écarts
- **Différence avec l'état suivant** (la version garde l'état d'avant une modification) : on voit ce que la modification a changé.
  Calculée dans le navigateur (versions déjà chargées, plus le contenu actuel lu dans `game_config`, lisible par tous).
- **Retour d'un groupe** = remplacer ce groupe des règles enregistrées par celui de la version (absent de la version : le groupe revient
  aux valeurs du code) ; les autres groupes ne bougent pas ; l'état d'avant est gardé (le retour se défait).
- **Garde de contenu sur tout retour** (section entière ou groupe) : une version devenue invalide est refusée, rien n'est écrit.
- **Réglages du serveur : partie réglée seulement** : casino = `settings` (jamais le pot, les gains récents, les tournois) ;
  générateurs = tout sauf `log` (le journal reste celui du moment) ; annonces, bandeaux, émojis = tout ; équipe = rôles, historique
  seul. Les données restaurées sont normalisées (`normalizeCasinoSettings` et `validateCasinoSettings`, `normalizeProcedural`…).
- Pas d'instantané quand un réglage suivi est réécrit sans changer sa partie réglée (passages du casino, journal des générateurs).
- `weekly_stock`, `patrons`, `server_pot` et les autres clés d'état ne sont pas suivis (état de jeu, pas des réglages).

### Questions proposées (à reporter dans `QUESTIONS.md`)
1. **Équipe : historique seul** (pas de retour arrière). Option : retour avec mise à jour des titres et de la liste des
   administrateurs. Retour arrière : `SETTINGS_HISTORY.staff.rollback = true` et la synchronisation des titres.
2. **Différence calculée dans le navigateur** (versions déjà chargées). Option : route serveur `content/diff` (versions anciennes non
   chargées). Retour arrière : sans objet.
3. **Liste des réglages suivis** : casino, générateurs, annonces, bandeaux, émojis, équipe. Option : y ajouter `weekly_stock` (offres
   de la semaine) et `patrons`. Retour arrière : retirer la clé de `SETTINGS_HISTORY`.
4. **Retour refusé si la version est devenue invalide** (garde de contenu). Option : permettre le retour et signaler les erreurs.
   Retour arrière : retirer `assertContentValid` de `contentRollback`.
