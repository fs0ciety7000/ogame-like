# 6.14.152 : Démarrage plus rapide : données demandées dès index.html, page préchargée, coque allégée (R4 É30-5b, R9 UX-12)

Type : ajustement (performance du front) + outillage (mesure) + tests
Statut : livré (branche `claude/hiver-k-s`, sans PR : Q12) ; mesure sur la pré-prod à refaire après le push
Proposition : aucune (pas d'effet sur les règles, l'équilibre ni les données des joueurs) ; source : constat RV-7 de la
[revue AU28](../audit/2026-10-08-au28-revue.md) (§4, mesures), AD-30, question 2 de [6.14.116](6.14.116-performance-mobile.md).
Lots R4 et R9 de la [feuille d'hiver 2031](../proposals/feuille-de-route-2031-hiver.md).

## Demande
R4 (É30-5b) et R9 (UX-12) ensemble : LCP mobile Galaxie 7,7 s, Commerce 8,1 s, Alliance 9,7 s sur la pré-prod ; l'élément est peint
au rendu de la page vers 8 s : c'est le démarrage (synchronisation de l'état, menu rendu d'un bloc) qui retarde, pas l'image. Mesure
avant, chemin critique, correction au plus juste (page avant la fin de la synchronisation, requêtes parallèles, code non critique
différé, menu progressif, préchargement des pages Galaxie / Commerce / Alliance), mesure après. Aucune règle de jeu ne change.

**Chemin critique sur la pré-prod** (mobile, Galaxie, un passage, prêt à 9,2 s) :
1. 0,8 s : la page HTML arrive ; le bloc d'entrée (381 Ko compressés, 1,1 Mo bruts, dont 1,1 Mo du moteur `src/game`) arrive à 4,5 s ;
2. 4,8 s : le code de la page (`GalaxyPage`) n'est demandé qu'après l'exécution de l'entrée ;
3. 5,0 s : le contenu du jeu (`game_config`, 33 Ko) est demandé, arrivé à 6,7 s ;
4. 5,4 s : la fiche du joueur (`players`, `queues`) n'est demandée qu'**après le premier rendu de la coque** (effet de
   `useGameSync`), arrivée à **7,6 s** : le réseau est encombré au même moment par une quinzaine de requêtes qui ne servent pas
   à afficher la page (fenêtres rares montées d'avance : annonce, bilan, Ctrl+K, raccourcis, rang, avec leurs icônes ; extensions
   de GSAP ; image de l'annonce de 86 Ko ; listes des joueurs, alliances, messages, signalements…) ;
5. 8,6 s : la page se rend (attente de `loading` et `contentLoaded` dans `AppShell`), l'élément du LCP se peint.

Les deux données qui retiennent la page (contenu, fiche du joueur) partent donc à 5 s, derrière deux allers-retours en chaîne
(entrée → coque → fiche), puis attendent leur tour sur un réseau saturé. Au même moment, le menu complet est calculé deux fois sur
téléphone (barre latérale cachée par CSS mais rendue, puis barre d'onglets), et au bureau ses groupes apparaissent puis
disparaissent (menu progressif) : c'était le pic de décalage de la question 2 de 6.14.116.

Composition du bloc d'entrée (`vite build`, modules) : `src/game` 1 101 Ko bruts, composants 291 Ko (menu 45 Ko), services 75 Ko,
icônes 51 Ko. Le moteur est dans l'entrée parce que `applyGameContent` (contenu personnalisé de l'admin) touche tous ses modules :
le découper est un chantier à part (voir Suites).

## Ce qui change
- Pour le joueur : la page ouverte s'affiche plus tôt ; le menu du bureau apparaît d'un coup à sa place ; annonce, bilan d'absence,
  Ctrl+K et raccourcis se préparent juste après l'affichage de la page (rien n'est perdu : Ctrl+K pressé avant les monte aussitôt).
- Pour l'admin : sans objet (aucun réglage de jeu).
- Dans le code :
  - `index.html` : script de tête (avant la feuille de style des polices, qui le retiendrait) : joueur connecté sur `/game…` →
    `game_config`, `players/<uid>` et `queues/<uid>` demandés tout de suite, avec le jeton de session (`pocketbase_auth`) ;
  - `src/lib/earlyData.ts` (nouveau) : `takeEarly` / `earlyOr` reprennent ces réponses **une fois**, pour le bon compte, moins de
    60 s après la demande ; toute erreur (jeton expiré, 404, compte suspendu) repasse par le SDK comme avant ;
    `contentService.startContentSync` et `playerService.loadInitial` (premier essai) les utilisent ;
  - `page-preload-plugin.ts` (nouveau, déclaré dans `vite.config.ts` et `tsconfig.node.json`) : le build écrit dans `index.html`,
    pour chaque adresse `/game/<segment>`, les fichiers de sa page hors entrée ; un script placé juste après le bloc d'entrée
    (avant la feuille de style du jeu) les précharge (`modulepreload`, priorité basse) ;
  - `src/lib/gameRoutes.ts` (nouveau) : `GAME_ROUTE_PAGES` sorti d'`App.tsx` (lu par le build) et `gameRoutePage(pathname)` ;
  - `NavBar.tsx` : une seule navigation rendue selon la largeur (`useDesktopNav`, 768 px) ; groupes du menu rendus quand la fiche du
    joueur est arrivée (`useNavReady`, pied de barre toujours là) ; place du rang réservée dans la barre réduite ;
  - `AppShell.tsx` : fenêtres rares montées après le premier rendu de la page (`useDeferredExtras` : moment libre, 2 s au plus) ;
  - `scripts/preprod-perf.mjs` : `PERF_TRACE=1` ; compte de mesure existant → jeton d'emprunt d'identité (`impersonate`, 2 h)
    au lieu de réécrire son mot de passe (la mesure n'écrit plus rien sur le serveur, hors synchronisation normale du jeu).

Lecture :
- en local, l'API répond en 0,3 s : le gain sur le « prêt » mobile est modeste (−0,6 s sur la Galaxie, −0,7 s sur l'accueil), et le
  bureau gagne 0,1 à 0,35 s. Sur la pré-prod, la fiche du joueur arrivait à 7,6 s derrière un réseau saturé : c'est là que
  le gain attendu est le plus fort (estimation : « prêt » ≈ fin de l'entrée 4,5 s + 2 s d'exécution ≈ 6,5 s au lieu de 8,5 à 9 s),
  **à confirmer par la mesure après le push** ;
- octets reçus jusqu'au calme du réseau : −160 à −285 Ko sur mobile (fenêtres rares différées) ;
- décalage au bureau : 0,03 → 0,005 à 0,012 (menu rendu en une fois : question 2 de 6.14.116 réglée) ;

  feuille de style du jeu ; celle-ci partage désormais le réseau avec les données et le code de la page (priorité basse essayée :
  sans effet en HTTP/1.1 local). Échange voulu : le texte des robots contre la page du joueur. Voir question 2.

**Poids des blocs** (`vite build`, compressés gzip) : entrée 376,0 → 376,5 Ko (table des pages sortie d'`App.tsx`, crochets), `vendor`

## Décisions et écarts
- **Données demandées par `index.html`** plutôt qu'au démarrage du module : c'est le seul moyen de les faire partir avant les 3 à
  4 s du bloc d'entrée sur mobile. Lecture seule, mêmes adresses et même jeton que le SDK, le serveur reste seul juge ; une réponse
  n'est reprise qu'une fois et pour le compte qui l'a demandée.
- **Page rendue dès que contenu et fiche sont là**, pas avant : afficher la page avec le contenu par défaut puis le remplacer
  changerait les chiffres sous les yeux du joueur (et remonterait la page). Le démarrage attend toujours ces deux lectures, qui
  arrivent maintenant pendant le téléchargement du code.
- **Menu** : groupes rendus en une fois (option de la question 2 de 6.14.116) ; sur téléphone la barre latérale n'est plus rendue.
- **Fenêtres rares** : montées au premier moment libre après la page (2 s au plus) ; l'annonce d'un compte neuf s'ouvre donc un peu
  plus tard, sans être perdue.
- **Séquence d'amorçage** (GSAP, une fois par session) gardée : effet voulu (DESIGN.md), et GSAP sert aussi au titre de la page.
- **Bloc d'entrée** non découpé : le moteur entier y est (1,1 Mo bruts) à cause d'`applyGameContent` ; chantier d'architecture
  chiffré en Suites, hors de ce lot « au plus juste ».

### Questions (reportées : Q376 à Q379 dans `QUESTIONS.md`)
1. **Données du démarrage demandées par `index.html`** (jeton de session lu dans le navigateur, trois lectures). Option : les demander
   au chargement du module (gain réduit d'environ 3 s sur mobile). Choix fait : `index.html`. Retour arrière : retirer le script de tête
   d'`index.html` (le jeu retombe sur le SDK sans autre changement).
2. **FCP mobile +0,25 s** (texte de la page statique) contre la page du jeu affichée plus tôt. Option : précharger la page seulement
   après la feuille de style (le préchargement attendrait alors ≈ 1 s). Choix fait : garder le préchargement tôt. Retour arrière :
   `insertPreloadScript` (`page-preload-plugin.ts`), placer le script après la feuille de style.
3. **Fenêtres rares différées** (annonce, bilan, Ctrl+K, raccourcis, rang, bilan de saison) d'au plus 2 s après la page. Option :
   les monter au démarrage comme avant. Choix fait : différer. Retour arrière : `useDeferredExtras` (`AppShell.tsx`) qui rend `true`.
4. **Découper le bloc d'entrée** (moteur chargé par page, ou contenu personnalisé appliqué à la demande) dans un lot à part (taille L) ?
   Choix fait : noté en suite, à décider après la mesure de la pré-prod.
