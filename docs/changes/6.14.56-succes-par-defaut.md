# 6.14.56 : succès par défaut toujours présents

Type : correctif
Statut : livré (branche de travail, sans PR)
Proposition : aucune (correctif, revue AU27 procédural : `docs/audit/2026-10-07-au27-procedural.md`, constat AP-1, lot AP-L1) ; ; choix Q113 à Q117 (`docs/QUESTIONS.md`)
feuille de route `feuille-de-route-2030-automne.md`, lot 2 ; choix Q82 (`docs/QUESTIONS.md`, validée)

## Demande
Livrer le lot AP-L1 de la revue AU27 : tout succès ajouté au code doit exister sur le serveur, même après que le générateur de paliers
a écrit la liste des succès en base.

## Diagnostic
- `proceduralTick` (`cosmic_db.js`) écrivait `content.achievements.concat(paliers)` dans `game_config.achievements` : la liste entière.
- `applyGameContent` prenait alors cette liste à la place des défauts (`overrides.achievements ?? defaults`), et aucune migration
  n'ajoutait les succès par défaut arrivés ensuite.
- Pré-prod (copie de la prod, AU27 §2.6) : 119 succès stockés, **4 succès par défaut absents** : `chapter_reader`, `chapter_keeper`,
  `seal_bearer`, `pass_finisher` (ajoutés en 6.9.2). La garde `contentChain.test.ts` restait verte (elle lit le code, pas la base).
- Preuve : `achievementsDefaults.test.ts` échoue sur le code d'avant le lot (2 tests sur 6 : succès absents, retrait exprès ignoré).

## Ce qui change
- Pour le joueur : les succès « Lecteur des Chroniques », « Gardien des Chroniques », « Porte-sceau » et « Jusqu'au bout » existent sur
  le serveur, et tout futur succès du code aussi (règle n° 4). Ceux déjà mérités se débloquent au prochain passage de la vérification
  des succès (mesures existantes : chapitres terminés, sceaux, passes finis).
- Pour l'admin :
  - un succès du code supprimé dans Admin → Contenu → Succès est noté dans **`achievementList.removedDefaults`** (réglage du registre,
    Admin → Règles → Tous les réglages → « Succès : succès par défaut retirés ») : il ne revient pas ;
  - « Valeurs par défaut » des succès vide cette liste (tous les succès du code reviennent, comme l'annonce le message de suppression) ;
  - les valeurs modifiées d'un succès (seuil, récompense…) restent celles de la base.
- Dans le code :
  - `achievements.ts` : `ACHIEVEMENT_LIST_RULES` (`removedDefaults`), `withDefaultAchievements(stored, removed)` (un succès complété se
    place après le succès par défaut qui le précède dans le code) ;
  - `content.ts` (`applyGameContent`) : liste enregistrée complétée, `removedDefaults` lu avant la fusion des règles ;
  - `ruleRegistry.ts` : groupe `achievementList` ;
  - `cosmic_db.js` (`proceduralTick`) : n'ajoute que ses nouveaux paliers à la liste **enregistrée** (relue dans la transaction), sans
    réécrire les succès complétés ni ceux retirés ;
  - `ContentEditor.tsx` : suppression d'un succès du code → `removedDefaults` ; « Valeurs par défaut » → liste vidée.

## Décisions et écarts
- Option prudente pour les données des joueurs (rien n'est retiré) : sans liste de retraits connue avant ce lot, **tout** succès par
  défaut absent est complété. Sur la pré-prod, ce sont exactement les 4 succès cités par l'audit ; si un admin en avait supprimé un
  exprès avant ce lot, il revient et se retire de nouveau dans l'admin (il est alors noté).
- Pas de migration ponctuelle : le complément se fait à chaque application du contenu (client et serveur), comme les succès dérivés.
  La liste en base n'est pas réécrite ; elle le sera par le prochain palier généré ou le prochain enregistrement dans l'admin.
- Sans liste enregistrée, le générateur écrit les défauts plus ses paliers (comme avant) : le complément protège les succès suivants.
- Q82 (paliers auto déjà créés) : gardés tels quels, rien n'est retiré ; le bridage des paliers reste le lot AP-L4.
