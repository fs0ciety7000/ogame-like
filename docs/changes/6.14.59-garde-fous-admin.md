## Demande
Livrer le lot AA1 de la revue AU27 : « `guardContentConfig` côté serveur ; validation récursive selon la forme du défaut ; `null` refusé
pour un nombre ; test : une liste d'objets mal formée est refusée ». Q75 validée : **refuser** les types et formes invalides, **avertir**
(sans bloquer) au-delà de ×2 / ÷2 du défaut.

## Diagnostic
- `validateRules` (`content.ts`) ne contrôlait que le premier niveau d'un groupe de règles. Les objets imbriqués et les listes d'objets
  (`alliances.researches`, `bounties.tiers`, `weeklyChallenge.tiers`…) n'étaient vus que comme « une liste » : une recherche d'alliance
  sans `perLevel` donnait `NaN` en jeu (AA-25).
- `mergeRuleGroup` (registre) garde un `null` saisi dans « Tous les réglages » : un nombre devenait `null` sans erreur.
- Le serveur ne vérifiait que la section « rules » (`guardRulesConfig`, `cosmic_db.js`) : unités, bâtiments, technos, reliques… n'étaient
  validés que par le navigateur (`ContentEditor`). Un appel direct à l'API (ou un brouillon resté invalide) enregistrait un contenu
  que `applyGameContent` applique ensuite à chaque action (AA-26).
- Pré-prod (copie de la prod, lecture seule, `game_config` lu en GET) : le contenu enregistré (règles, unités, bâtiments, technos, succès,
  passes…) passe la nouvelle validation **sans aucune erreur** ; la garde ne bloque donc rien de ce qui tourne aujourd'hui.

## Ce qui change
- Pour le joueur : rien de visible ; un réglage cassé ne peut plus atteindre le jeu (plus de `NaN` ni de plantage d'action).
- Pour l'admin :
  - toute section de contenu (règles, unités, bâtiments, technologies, reliques, missions, succès, passes…) est vérifiée **par le
    serveur** à l'enregistrement. Un refus dit le champ et le type attendu, par exemple « Contenu refusé : Unité Frégate :
    « cost.scrap » doit être un nombre, reçu : vide (null). » (trois erreurs au plus, puis « +N autres ») ;
  - dans l'éditeur, les mêmes erreurs s'affichent avant l'enregistrement (liste « À corriger ») : `ContentEditor` et l'onglet Règles
    appellent la même validation que le serveur ;
  - onglet Règles : encadré **« À vérifier (non bloquant) »** qui liste les nombres à plus de ×2 (ou moins de ÷2) de leur valeur par
    défaut (Q75). L'enregistrement reste possible.
- Dans le code :
  - `src/game/contentShape.ts` (nouveau, moteur pur) : `shapeErrors`, `listShapeErrors` (validation récursive selon la forme du défaut),
    `driftWarnings` (écarts ×2) ;
  - `content.ts` : `validateRules` descend dans les objets et listes d'objets ; `validateGameContent` vérifie la forme des bâtiments,
    unités, technos et reliques, et refuse une section de liste qui n'est pas une liste ; `resolveGameContent` (fusion pure, extraite
    d'`applyGameContent`) ; `contentSectionErrors(section, data, stored)` ; `ruleDriftWarnings` ; `CONTENT_SECTION_LABELS` ;
  - `hooksEntry.ts` : export de `contentSectionErrors` ;
  - `cosmic_db.js` : `guardContentConfig` (toutes les sections de `CONTENT_SECTIONS`) ; `guardRulesConfig` devient un alias ;
  - `cosmic.pb.js` : `onRecordCreateRequest` / `onRecordUpdateRequest` de `game_config` appellent `guardContentConfig` ;
  - `src/pages/admin/panels.tsx` : encadré d'avertissements de l'onglet Règles.

## Décisions et écarts
- **Règles de forme** (Q75, refus) : un nombre reste un nombre fini, à toute profondeur (`null`, texte, `NaN` refusés) ; il n'est pas
  négatif quand tous les défauts connus sont positifs ou nuls ; oui/non, texte, liste et objet gardent leur type ; un élément de liste
  d'objets est comparé à **tous** les éléments par défaut : un champ chiffré (nombre, liste, objet) présent dans tous est obligatoire.
  `null` reste permis là où le défaut vaut `null` (« ancien comportement ») et pour un objet (fusionné champ par champ).
- **Tolérances prudentes** (choix non tranché par l'audit, noté ici) : une clé inconnue du défaut passe (contenu ajouté, champ optionnel) ;
  un texte ou un oui/non absent d'un élément ne bloque pas (rien ne casse) ; pas de borne haute générique (bornes par champ : lot AA2,
  métadonnées `*_RULES_META`).
- **Seules les erreurs nouvelles bloquent** : le serveur compare le contenu enregistré avec et sans la modification. Une erreur déjà en
  base dans une autre section ne bloque pas l'admin (le plus prudent pour un serveur en service : on ne fige pas l'admin sur un contenu
  hérité). Sur la pré-prod il n'y en a aucune.
- Les écritures du serveur lui-même (générateur, migrations, retour arrière) ne passent pas par la garde (`onRecord…Request` ne voit que
  les requêtes) : elles écrivent du contenu produit par le moteur.
- La fusion du contenu pour la validation est pure (`resolveGameContent`) : valider n'applique rien au moteur du serveur.
- L'avertissement ×2 compare les nombres des deux premiers niveaux d'un groupe (pas les listes) : assez pour signaler une faute de
  frappe, sans noyer l'admin.
