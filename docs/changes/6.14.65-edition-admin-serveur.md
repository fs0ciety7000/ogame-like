## Demande
Livrer le lot AC-B de la revue AU27 : l'éditeur de fiche joueur de l'admin ne doit plus réécrire une fiche à partir de la liste chargée à
l'ouverture. Action `edit` de `admin/player-action` qui applique des différences sur l'état rattrapé, relu dans la transaction, sous les
plafonds, avec motif et journal ; remise à zéro de l'XP côté serveur ; plus aucune écriture directe du client sur `players` depuis l'admin.

## Diagnostic
- AC-2 (🔴) : `adminUpdatePlayer` (`adminService.ts`) envoyait `resources`, `buildings`, `units`, `techLevels`, `xp`, `seasonXp` du
  brouillon, construit sur `adminListPlayers()` au chargement du panneau. Aucun rattrapage, hangar non vérifié. Exemple de l'audit :
  l'admin corrige une relique en 10 min ; entre-temps le joueur dépense 50 000 ferraille et lance sa flotte ; la sauvegarde rend la
  ferraille et les unités parties (doublées au retour) et efface 10 min de production.
- `adminResetAllXp` : boucle du client, une écriture par joueur, non atomique (interrompue = moitié des joueurs remis à zéro).
- La règle d'API `players.updateRule` donnait toute l'écriture aux admins du jeu : le chemin restait ouvert même sans l'éditeur.

## Ce qui change
- Pour le joueur : une correction de l'équipe ne peut plus effacer ce qu'il a fait depuis l'ouverture de sa fiche ; il reçoit une
  notification « Empire ajusté par l'équipe » avec le motif.
- Pour l'admin (Admin → Joueurs) :
  - l'éditeur n'envoie que les écarts saisis (« Enregistrer » grisé tant que rien n'a changé ; le toast dit combien de changements) ;
  - le serveur ajoute ces écarts à la fiche du moment, rattrapée : 4 chasseurs affichés passés à 3 retirent 1 chasseur, même si le
    joueur en a construit 6 entre-temps ;
  - plafonds : niveau de bâtiment, de techno et d'unité dans [0, niveau maximal] ; une ressource commune ne monte pas au-delà de
    l'entrepôt (un stock déjà au-delà est gardé ; au-delà, « Rendre des ressources ») ; une hausse d'unités, ou un hangar baissé, ne
    crée ni n'aggrave une surcharge (`hangarLoad`, vaisseaux en vol comptés) ; un retrait plus grand que le stock s'arrête à 0 ;
  - motif obligatoire (5 caractères), journal champ par champ (`resources.scrap`, `units.chasseur`… avant et après) ;
  - « Remettre toute l'XP à zéro » (Outils) : une seule transaction côté serveur, une ligne au journal.
- Dans le code :
  - moteur : `src/game/adminEdit.ts` (`adminEditDiff`, `adminEditCount`, `applyAdminEdit`, `ADMIN_EDIT_DEFAULTS`), exporté dans
    `hooksEntry.ts` ;
  - serveur (`cosmic_db.js`) : action `edit` et `resetAllXp` dans `adminPlayerAction` ; `SCHEMA_RULE_SYNC` dans `ensureSchema` ;
  - schéma : `players.updateRule` sans la clause des admins du jeu (le superutilisateur PocketBase garde l'accès, journalisé avec motif
    par `requireAdminReason`) ;
  - client : `adminEditPlayer(id, changes, reason)` et `adminResetAllXp()` par la route ; `adminUpdatePlayer` supprimé ; `panels.tsx`.

### Route
`POST /api/cosmic/admin/player-action` (admin du jeu ou superutilisateur ; sinon 403 « Réservé aux administrateurs du jeu. »)
- `{ uid, action: "edit", reason, changes }`, `changes` = `{ xp?, seasonXp?, resources?: { <res>: écart }, buildings?: { <id>: { level?: écart,
  unlocked?: booléen } }, units?: { <id>: { level?: écart, count?: écart } }, techLevels?: { <id>: écart } }`.
  Réponse 200 : `{ "<champ>": { avant, après }, … }`. Erreurs 400 : motif absent ou trop court ; « Aucune modification à enregistrer. » ;
  identifiant inconnu ; valeur invalide (non numérique ou au-delà de 10^12) ; niveau hors limites ; « Entrepôt : … +N au plus » ;
  « Hangar d'attaque / de défense : N place(s) de trop ». Joueur introuvable : 400. Rien n'est écrit sur un refus.
- `{ action: "resetAllXp", confirm: "RESET", reason? }` (sans `uid`) : réponse `{ players }` (fiches remises à zéro) ; 400 si la confirmation manque.

## Décisions et écarts
Choix pris seul, option la plus prudente pour les données des joueurs (à reporter dans `docs/QUESTIONS.md` par l'agent principal) :
- Tous les nombres partent en **écarts**, niveaux compris (et non en valeur cible) : une hausse de niveau faite par le joueur pendant
  l'édition n'est jamais annulée ; un écart qui ferait dépasser le niveau maximal est refusé, pas tronqué.
- Ressource commune au-delà de l'entrepôt : **refus** avec la marge restante, plutôt qu'une troncature silencieuse ; la compensation au-delà
  passe par « Rendre des ressources » (action `grant`, inchangée).
- Retrait plus grand que le stock : arrêté à 0 (le journal montre la valeur obtenue).
- Le joueur est prévenu de chaque édition (notification avec le motif), comme pour les cadeaux de l'équipe.
- `resetAllXp` garde la portée d'avant (tous les enregistrements `players`, seigneurs compris : leur XP se recale seule sur celle des joueurs).
- `players.updateRule` resserré : l'admin du jeu n'écrit plus la fiche d'un autre joueur par l'API (défense en profondeur). Le superutilisateur
  PocketBase n'est pas concerné. Retour arrière : remettre `|| (@request.auth.id != "" && @collection.admins.id ?= @request.auth.id)` dans
  `pb_schema.json` (recopié au démarrage par `SCHEMA_RULE_SYNC`).
- « Vider les files » (`adminClearQueues`) reste une écriture directe de `queues` par l'admin : elle remet à vide, sans lecture ancienne
  (hors périmètre d'AC-2).
