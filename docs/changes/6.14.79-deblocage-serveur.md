# 6.14.79 : déblocage progressif, serveur (objectifs du jour, « Nouveau : … »)

Type : fonctionnalité (moteur, serveur)
Statut : livré (branche de travail, sans commit à la livraison du lot) ; essai sur la pré-prod au prochain push
Proposition : [`docs/proposals/deblocage-progressif.md`](../proposals/deblocage-progressif.md) §5.4, §5.6, §5.8, lot DP-L4 ; Q152 à Q158 ; choix Q184 à Q201 (`docs/QUESTIONS.md`)
(validées), Q156 (« Tout afficher » ouvre aussi les objectifs), Q158 (objectifs filtrés) ; choix du lot listés ci-dessous (à reporter
dans `docs/QUESTIONS.md`, non écrit : consigne du lot) ; feuille de route `feuille-de-route-2030-automne.md`, lot 51d.

## Demande
Lot DP-L4 : objectifs du jour tirés seulement parmi les systèmes ouverts du joueur pour les **nouveaux jours** (`navUnlock.filterContracts`,
invariant I31), une notification « Nouveau : … » quand un palier ouvre des pages (une seule par palier, dans le circuit des notifications,
pas de nouvelle pastille), export dans `hooksEntry.ts`, jamais d'enregistrement d'un joueur lu hors transaction (I24).
Problème joueur : un compte neuf pouvait tirer « Gagner une attaque » ou « Acheter au marché » à J0, et une page s'ouvrait sans qu'il le sache.

## Diagnostic
- `ensureContracts` (`contracts.ts`) tirait parmi les 10 types sans regarder le menu ; il tourne dans `flushState`, côté serveur seulement
  (le client ne rejoue pas le flush) : le filtre peut lire la fiche du joueur sans risque d'écart client/serveur.
- 4 types se font sur une page toujours visible (amélioration, recherche, unités, dépense) : autant que d'objectifs par jour
  (`CONTRACT_RULES.perDay` = 4), le compte neuf a donc toujours ses 4 objectifs.
- Aucune trace côté serveur des pages déjà annoncées : il fallait une mémoire pour n'envoyer qu'une notification par ouverture.

## Ce qui change
- Pour le joueur (compte neuf, menu progressif) :
  - un nouveau jour ne tire que des objectifs dont la page est au menu ; la relance aussi (sans autre type ouvert : « Aucun autre objectif
    n'est encore ouvert : ta relance reste disponible. », la relance n'est pas consommée) ; le jour en cours n'est jamais refait ;
  - une notification « Nouveau : Galaxie, Alliance et … » (genre `system`, cloche et Journal, lien vers la première page) à chaque
    ouverture : rang atteint (« Tu as atteint Fer II : de nouvelles pages s'ouvrent. »), danger (« Une menace vise ton empire… »), fin de
    protection, étape du tutoriel, signal d'usage (« Débloqué avec ta première unité. ») ;
  - une page annoncée reste ouverte, même si son déclencheur disparaît (alliance quittée…).
- Pour un compte existant (créé avant la date et au moins Fer II), un admin ou `enabled` à faux : rien (aucune notification, rien
  d'écrit). « Tout afficher » : la mémoire suit en silence.
- Pour l'admin : `navUnlock.filterContracts` (déjà au registre) est maintenant lu par le serveur.
- Dans le code :
  - `src/game/contracts.ts` : `CONTRACT_PAGES`, `openContractTypes` ; `ensureContracts` (nouveau jour et complément du jour) et
    `rerollContract` tirent parmi les types ouverts ;
  - `src/game/navUnlock.ts` : `NAV_PAGE_LABELS`, `navPageLabel`, `navPageList`, `navAnnounced`, `navOpeningNotice` ; `navOpenReason` lit
    `stats.navAnnounced` en dernier recours (« mark ») ;
  - `src/game/stats.ts` : `PlayerStats.navAnnounced` (clé de `stats`, champ JSON existant : pas de nouveau champ de schéma) ;
  - `src/server/hooksEntry.ts` : export de `navOpeningNotice` et `navOpenPages` ;
  - `pocketbase/pb_hooks/cosmic_db.js` : `navOpeningNotice(e, game, player, notifications, now)` (exportée) ;
    `pocketbase/pb_hooks/cosmic.pb.js` : appelée dans la transaction de `/api/cosmic/action`, après `performPlayerAction` et le raid
    scripté, avant `savePlayer` (I24) ;
  - `pocketbase/pb_hooks/cosmic_game.js` régénéré.

## Décisions et écarts
- **« Une seule par palier »** lu comme « une notification par ouverture » : toutes les pages ouvertes au même passage sont citées dans
  une seule notification (un compte qui passe de 0 à Fer II d'un coup reçoit une notification pour Fer III et Fer II). Plus sobre qu'une
  notification par rang ; aucune page n'est annoncée deux fois.
- **Mémoire** dans `stats.navAnnounced` (pages réglées, 27 au plus) plutôt qu'un nouveau champ de profil ou des marques dans
  `announcementsSeen` (limite de 120 identifiants, `nav:` voulant dire « visitée » pour la pastille « Nouveau »).
- **Première lecture** (compte d'avant le lot, mémoire absente) : les pages déjà ouvertes sont notées sans notification, pour ne pas
  annoncer des pages connues depuis des jours. Un compte neuf passe par là à sa première action (J0 : rien d'ouvert, mémoire vide).
- **Page visitée** (marque `nav:` ou astuce `tip:`) : notée sans notification.
- **Danger côté serveur** : lu sur la fiche (combat subi, raid scripté lancé, ultimatum, menace de faction) ; une flotte hostile encore en
  vol n'est pas lue par la route des actions (une requête de plus par action) : le client ouvre déjà les pages et pose la marque `nav:`.
- **Admin** : vérifié seulement quand une notification est à envoyer (`isGameAdmin` coûte une lecture) ; la mémoire est tout de même tenue.
- **Objectifs d'un admin neuf** : filtrés comme ceux d'un joueur (le tirage ne connaît pas le rôle) ; sans effet pratique.
- **Relance sans type ouvert** : refusée avec un message, relance gardée (plus prudent que de tirer un objectif infaisable).
- **Complément du jour** (passage de 3 à 4 objectifs, ou `perDay` relevé dans l'admin) : complété avec des types ouverts seulement ; s'il
  manque des types, le jour garde moins d'objectifs (jamais un objectif infaisable).
- Types → pages : attaque et sondes → Galaxie ; défense → Combats ; missions → Missions ; marché et dons → Commerce (dons : page des
  échanges, choix le plus proche de la proposition §5.8).

Questions à reporter dans `docs/QUESTIONS.md` (non écrit, consigne du lot) : une notification par ouverture (et non par rang) ; mémoire
`stats.navAnnounced` ; première lecture silencieuse ; relance refusée sans type ouvert ; danger serveur lu sur la fiche seulement.
Retour arrière : `navUnlock.filterContracts` à faux (objectifs) ; `navUnlock.enabled` à faux (tout).
